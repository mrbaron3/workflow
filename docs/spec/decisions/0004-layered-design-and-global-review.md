# 決定記録 0004: 設計の三層化（system / epic / slice）と層別・大域整合の独立審査

- 状態: 確定
- 最終更新: 2026-06-18
- 影響モジュール: M21 Design Planner / M22 Design Reviewer / M03 Coordinator（epic 状態機械の設計サブ状態）/
  M18 Storage（system 層成果物の住処）/ ADR-0003（contract altitude を tier 別適用へ精密化）
- 正本差分: REQUIREMENTS.md への上書きなし（設計層の内部構造を精密化するもの）

## 1. 背景

[ADR-0001](0001-authoring-execution-split.md) が WHAT（オーサリング）と HOW（設計・実装）を分離し、
[ADR-0002](0002-independent-design-review.md) が設計の独立審査を、[ADR-0003](0003-spec-altitude-and-dry.md)
が設計の高度（contract altitude）を定めた。しかし設計の出力は **epic 共有の spine（決定の寄せ集め）＋
PR サイズの slice** の2段しかなく、spine が **ドメイン・データ・アーキを未分化に1リストへ詰めていた**。
ここに2つの欠陥がある。

- **(a) 粒度が粗すぎる**: ドメインモデル・データ（スキーマ）・モジュール境界は altitude も審査観点も
  異なるのに、1つの「設計」へ畳まれ、層別の審査ができなかった。
- **(b) 所有者を取り違えていた**: ドメインマップ・データ設計・アーキは **system 全体で単一**でなければ
  矛盾し compose しない。これを epic ローカルの spine に置くと epic ごとに分岐し、整合が取れない。

本 ADR で設計を三層に解凍し、system 層を **global な単一 SoT** に格上げし、審査を **層別・大域整合**に
拡張する。

## 2. 確定した決定（理由つき）

| # | 決定 | 理由 |
| --- | --- | --- |
| D30 | 設計を三層に分割: **system**（ドメインマップ / データ設計 / アーキ）/ **epic**（仕様＋設計デルタ＋コンポーネント）/ **slice**（seam・PR サイズ）。旧「spine＋slice」の spine を解凍する | 設計は単一概念でなく、altitude も審査観点も所有者も違う層の束。未分化な決定リストは粒度が粗く、層別審査ができない |
| D31 | system 層（ドメインマップ・データ設計・アーキ）は **全体で単一の生きた SoT・追加のみ**（epic ローカルでない）。epic はこれを**読み、必要時だけ追加的に拡張するデルタ**を出す。触る層が少ないことは可（adaptive）だが、層は常に global | ドメイン/データ/アーキを epic ごとに作ると矛盾し compose しない。整合は epic を超えた system（or 境界づけられたコンテキスト）単位でしか取れない |
| D32 | system 層への拡張は **大域整合審査**: 設計審査役が**全体（or 境界づけられたコンテキスト単位）**で整合を見る。epic 内整合では不十分 | 別 epic が同じ概念を別名で重複追加する／スキーマが既存と矛盾する、は全体を見ないと検出できない |
| D33 | 審査の効かせ方: 最薄ループは **1パス＋層別セクション**（層別観点を1枚のスコアカードに集約）。上流の高コスト層（ドメイン・データ）は価値確認後に **先行ゲート**へ昇格する | shift-left の価値（上流誤りを下流着工前に潰す）と「最薄の縦1本」（README §8）の両立。最初から多段ゲートは重い |
| D34 | **γ 二層化**: 設計立案役が書き設計審査役がゲートするのは **contract altitude（層を跨ぐ約束）のみ**。アルゴリズム・内部データ構造・最適化等の内部実装は、人間が固定したい時だけの **非ゲートの「実装メモ」**。ADR-0003 の altitude ルールを tier 別に適用し、advisory carve-out を加える | 金が動く所は人間がアルゴリズムを pin したい一方、内部 HOW を強制すると有能なモデルの品質を下げ陳腐化する。強制は契約 altitude、固定は任意 |
| D35 | 文書種別の線引き: **人間が所有・編集する文書**（仕様書・各 tier の設計書）は**リッチ Markdown**、**機械が受け渡す成果物**（スコアカード・Issue 契約・spawn 指示・承認参照）は**構造化データ**。層間の差し戻しは既存の逆引き機構を tier 間に適用する（新機構不要・additive） | YAML 化は人間文書の可読性を損なう（D15 と同根）。機械契約は構造化が正しい。差し戻しの局所化機構は既にある |

## 3. 三層の構造とデータフロー

```text
system 層（global・単一の生きた SoT・追加のみ・全 epic が参照）
  ├─ domain-map.md     ドメインマップ（ユビキタス言語・エンティティ/集約・関係・境界・ドメイン不変条件）
  ├─ data-model.md     データ設計（論理モデル → スキーマ・所有・移行戦略・永続化契約）
  └─ architecture.md   アーキ（モジュール境界・seam・共有基盤・横断方針）
        ▲ 読む / 必要時のみ追加的に拡張（デルタ）        ▲ 大域整合審査（全体 or 境界コンテキスト単位）
        │                                                │
epic 層（1 spec.md = 1 epic）
  ├─ spec.md            WHAT（人間署名・オーサリング層の SoT）
  ├─ design-delta.md    どの system 層をどう拡張するか（epic の設計判断・追加分のみ）
  └─ slices/SLICE-*.md  コンポーネント/スライス設計（PR サイズ・seam まで）
        ▲ 被覆/排他・上位層への背反なし・受け入れ要件意図の充足
        │
slice / PR 層
  └─ 実装は M06 Generator。設計はスライスの seam まで。内部実装（アルゴリズム等）は
     非ゲートの「実装メモ」として人間が任意で pin（D34）
```

各 tier の性質:

- **system**: 所有 = 全体。寿命 = 長寿命。進化 = 追加のみ（既存を巻き戻さない・renumber しない）。
  整合スコープ = global（or 境界づけられたコンテキスト）。
- **epic**: 所有 = epic。出力 = system 層への**デルタ**（読む＋必要時拡張）＋ コンポーネント設計。
  adaptive = デルタを出す層は少なくてよいが、整合は常に global（D31）。
- **slice**: 所有 = PR。seam・契約まで。内部 HOW は実装メモ（非ゲート）。

審査（設計審査役）は層別観点で行う:

- ドメインマップ: 言語の一貫性／概念の重複・欠落／境界の妥当性／不変条件の自己無矛盾（**全体に対して**）。
- データ設計: ドメインマップとの整合／所有・正規化の妥当性／移行の後方互換／永続化契約の一貫性（**全体に対して**）。
- アーキ: モジュール境界の coherence／seam の噛み合い／共有基盤の重複なし（**全体に対して**）。
- コンポーネント/スライス: 被覆/排他／スライス間整合／上位層への背反なし／受け入れ要件意図の充足（epic 内）。

## 4. system 層成果物の住処（M18 連動）

system 層は epic ディレクトリの**外**に、全 epic が参照する単一の場所に置く（住処の具体は M18 / 設計立案役
確定時に固定。下記は提案・調整可）:

```text
specs/
  _system/                 # system 層（global・単一 SoT）
    domain-map.md
    data-model.md
    architecture.md
  <epic>/                  # epic 層
    spec.md
    acceptance.yaml
    manual-requirements.md
    design-delta.md
    slices/SLICE-<EPIC>-NNN.md
```

epic の `design-delta.md` と各スライスは、参照する system 層成果物を **版固定参照（path + 版）** で指す
（ADR-0001 D8 の参照渡し・版固定原則を system 層へ拡張）。これにより「どの版の global 設計に対して
拡張したか」が固定され、system 層が後で進化しても epic の設計入力は決定的に再現できる。

## 5. ADR-0003（contract altitude）との関係

本 ADR は ADR-0003 を**上書きしない**。altitude ルール（決定＋モジュール間契約/seam までを書き、クラス内部
設計を書かない）を **tier ごとに適用**し、γ（D34）の advisory carve-out を加えて精密化する:

- 各 tier が書くのは **その tier で他の独立ユニットと噛み合うために必要な約束**（contract altitude）。
- アルゴリズム・内部データ構造・最適化は、どの tier でも**契約ではない**ため強制しない。人間が固定したい
  ときだけ**非ゲートの実装メモ**として残す（金が動く所の pin を許すが、ゲートにはしない）。
- 「契約 altitude か実装メモか」の判定は ADR-0003 D26 の記載テスト（「これが無いと別の独立ユニットが
  非整合になるか？」）をそのまま使う。Yes → その tier の契約として書く。No → 実装メモ（任意・非ゲート）。

## 6. 残 open

- system 層成果物の正確な住処・粒度（domain-map を境界コンテキスト単位で分割するか1枚か）。M18 / 設計立案役 確定時。
- 大域整合審査の **決定的部分**（名前衝突・参照整合・重複エンティティ検出）と **判断部分**（意味的重複・
  概念の別名重複）の振り分け。設計審査役 確定時。
- ドメイン/データ層を loop 2 で**先行ゲート**へ昇格する判断契機（D33）。操作的しきいは焼かず観測から起こす。
- epic 設計デルタ（`design-delta.md`）の具体スキーマ（拡張した system 層成果物の参照と、追加した要素の最小記述）。設計立案役 確定時。
