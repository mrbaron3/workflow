# 多観点パネル採点（evaluator panel）受け入れ要件

> このファイルは Development Department への入力契約であり、人間が機能の **WHAT（受け入れ基準）** を
> 著す source of truth。frontmatter は持たない（meta・署名は ApprovedSpecRef が持つ）。
>
> **WHAT/HOW 境界**: 本 spec が定義するのは「完了した実装 sample が**複数の独立した観点**で採点され、
> その観点別記録から sample の最終判定が**決定論的に導出**され、修復と計数が観点別記録の存在に耐える、
> その**観測可能な性質**」。観点採点の実行機構（独立セッション／並行度／どの観点を LLM が担うか／
> コスト既定）は設計層が持つ（[ADR-0006](../../decisions/ADR-0006-evaluator-panel-sessions-and-github-pr-gate.md)
> → system 層 execution へ吸収）。本 spec の AC は機構を指定しない。
>
> **meta-feature の層分け**: 本機能はハーネス自身の機構（評価パネル）を作る。観点セットの定義・集約の
> 不変条件・観点タグの形は **system 層（execution コンテキスト）** が所有し、本 spec は参照する
> （dependsOn は acceptance.yaml）。人間審査ゲート（GitHub PR）と watch 常駐は**別 spec**（本 spec の
> スコープ外。sample の最終判定が出た後の遷移はゲート spec が定める）。
>
> **参照する固定制約**: [NORTH_STAR](../../NORTH_STAR.md)（証拠で評価・false-pass を放置しない）／
> ADR-0003（hard gate は score より先）／ ADR-0006（パネル実行モデル・premises E1-E7）／
> system 層 `_system/execution/`（観点＝`LANG-execution-010`・パネル＝`LANG-execution-009`・
> 集約不変条件＝`DOM-execution-004`・観点タグ＝`DATA-execution-001`）。

## サブ機能一覧

> この一覧は設計層への分割境界ヒントであり、slice ではない。

| ID | サブ機能 | 優先度 |
| --- | --- | --- |
| PANEL-A | 観点別採点（完了 sample を全観点で採点し観点タグ付き記録を残す） | 高 |
| PANEL-B | 集約と修復指示（blocker 優先の決定論導出・観点横断の修復指示） | 高 |
| PANEL-C | 耐障害・保全（不正出力の昇格・成果物の不変・部分再開・計数の非二重化） | 高 |

## PANEL-A 観点別採点

**ユーザーストーリー**

- 誰が: 進行管理役（ハーネス）
- 何を: 完了した実装 sample を、単一の合成採点でなく**観点ごとに独立した採点記録**として残す
- なぜ: 単一 verdict は「どの観点の問題か」を潰してしまい、修復指示も改善分析（どの観点で落ちやすいか）も
  粗くなる。観点別の記録が修復・回帰・改善ループの分解能を与える（北極星: 評価・改善）

**事前条件**

- 実装層の 1 sample 実走行（実装完了 → 実検証 → 採点記録）が既に成立している（実装済み・execution 層）。
- 観点タグの置き場（採点記録の観点フィールド）は system 層が定義済み（`DATA-execution-001`）。

**受け入れ基準**

- **[AC-PANEL-001] 正常系: 完了 sample が全観点で採点される**
  - Given hard gate（build / typecheck / tests 等）を通過した完了 sample がある
  - When パネルが採点する
  - Then 定義された全観点それぞれについて観点タグ付きの採点記録が **1 件ずつ**残り、各記録は
    verdict と、根拠（expected / observed / 再現手順・evidence への参照）を持つ findings を備える

- **[AC-PANEL-002] 境界: hard gate を通らない試行は観点採点に進まない**
  - Given hard gate が fail する試行がある
  - When その試行を評価する
  - Then 観点別採点は行われず（その試行に観点タグ付き記録が増えない）、gate の failing findings から
    修復指示が組まれる（hard gate は score より先、の観点版）

## PANEL-B 集約と修復指示

**ユーザーストーリー**

- 誰が: 進行管理役（ハーネス）
- 何を: 観点別記録から sample の最終判定を決定論的に導出し、観点横断の修復指示を組む
- なぜ: 判定の導出が決定論でなければ resume・監査で同じ結論を再構成できない。修復指示に発生源観点が
  無ければ、Generator は直す優先順位を誤り、改善ループは「どの観点の指摘が効いたか」を測れない

**受け入れ基準**

- **[AC-PANEL-003] 正常系: 最終判定は blocker 優先で導出され、スコアで相殺されない**
  - Given 観点別採点記録が揃っており、いずれか 1 観点に blocker の findings があり verdict が request_changes である
  - When sample の最終判定を導出する
  - Then 最終判定は request_changes になる（他観点のスコア・verdict がどれほど良くても相殺されない）

- **[AC-PANEL-004] 正常系: 全観点 approve で sample が approve になる**
  - Given 全観点の採点記録の verdict が approve である
  - When sample の最終判定を導出する
  - Then 最終判定は approve として導出される（以降の遷移はゲート spec が定める）。導出は保存された
    集約値でなく観点別記録から行われ、同じ記録集合からは常に同じ判定が得られる

- **[AC-PANEL-005] 正常系: 修復指示は観点横断で、発生源観点が判る**
  - Given 複数の観点が findings を出した採点結果がある
  - When 修復指示を組む
  - Then blocker の findings が優先され、同一基準への重複指摘は 1 つに束ねられ、各指示から
    **どの観点に由来するか**が判別できる

## PANEL-C 耐障害・保全

**ユーザーストーリー**

- 誰が: 進行管理役（ハーネス）
- 何を: 観点採点の失敗・中断・記録の増加が、判定の信頼性と計数を壊さないよう守る
- なぜ: 観点採点の出力は非決定な実エージェント由来であり、不正出力・中断は必ず起こる。それが
  「静かに合格へ倒れる」「二重計上される」形で漏れると、false-pass 放置という北極星の反証そのものになる

**受け入れ基準**

- **[AC-PANEL-006] 異常系: 不正な観点出力は静かに合格へ倒れない**
  - Given ある観点の採点出力が契約（schema）検証に失敗する
  - When 定められた再試行を尽くしても有効な出力が得られない
  - Then 当該 issue は人間審査へ昇格（needs-human-review）し、その観点が approve として扱われたり
    無視されたりして最終判定が approve になることはない

- **[AC-PANEL-007] 耐障害性: 部分完了からの再開で二重採点しない**
  - Given 一部の観点だけ採点記録が残った中断状態がある
  - When 同じ sample の採点を再開する
  - Then 未完の観点だけが採点され、同一の（PR・attempt・観点）に対する採点記録は 1 件のままである

- **[AC-PANEL-008] 境界: 観点採点は実装成果物を変更しない**
  - Given 採点対象の sample（変更ファイル集合を含む）がある
  - When パネルが採点する
  - Then 実装成果物（変更ファイル集合・その内容）は採点の前後で不変であり、スコープ判定の結果も
    採点によって変化しない

- **[AC-PANEL-009] 耐障害性: 観点別記録が既存の計数を二重化しない**
  - Given 1 つの attempt に観点数ぶんの採点記録が存在する
  - When メトリクス（pass@k / pass^k 等)・回帰昇格（Curator）を計算する
  - Then attempt / sample の数え方は観点数に影響されず（1 attempt は 1 と数える）、回帰昇格が
    観点数ぶん重複して作られない

**非機能要件**

- 決定論: 最終判定の導出・修復指示の組み立ては、同じ観点別記録の集合から常に同じ結果を返す。
- 可観測性: 観点別採点記録はそれぞれ evidence（根拠）への参照を持ち、進行管理役が状態と evidence
  だけから resume・監査できる。
- コスト: 観点採点は hard gate 通過後の試行に対してのみ行われる（AC-PANEL-002 が採点面から固定する）。

**完了条件**

- 自動テスト: 正常（全観点記録・blocker 優先導出・観点横断修復指示）／異常（不正出力の昇格）／
  耐障害性（部分再開・計数の非二重化・成果物不変）を各 1 以上。
- データ確認: 採点後の永続状態（観点タグ付き記録の件数・導出された最終判定・修復指示の発生源観点）が
  期待どおりであること。

## レッドライン

> 実装が**絶対にしてはならない**こと。Generator への明示的禁止。

- 最終判定をスコア平均で導出して blocker を相殺しない（`DOM-execution-004` を破らない）。
- 契約検証に失敗した観点出力を、無視・既定値補完・省略のいずれによっても **approve 側へ倒さない**。
- 観点採点が実装成果物（変更ファイル集合）を変更しない。
- 集約値を永続保存しない（最終判定は常に観点別記録から導出する。`DATA-execution-001`）。
- 観点セットの定義・集約の不変条件を本 spec や実装に重複記述しない（system 層を参照する）。
- 既存の単一採点記録（観点タグ無し）の読み手を壊さない（additive・後方互換）。
