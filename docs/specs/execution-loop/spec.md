# 自律実行ループ（drive ＋ 審査ゲート）受け入れ要件

> このファイルは Development Department への入力契約であり、人間が機能の **WHAT（受け入れ基準）** を
> 著す source of truth。frontmatter は持たない（meta・署名は ApprovedSpecRef が持つ）。
>
> **WHAT/HOW 境界**: 本 spec が定義するのは「実装対象として明示指定された issue が、人間の HOW 関与なく
> 実装〜評価まで自律で進み、**リリースだけは人間の判断点で止まり、その判断が証拠として残る**、その
> **観測可能な性質**」。駆動の機構（poll 常駐・セッション・tmux）とゲート UI（承認判断の入力元）は
> 設計層が持つ（[ADR-0005](../../decisions/ADR-0005-execution-layer-tmux-orchestration.md) L1／
> [ADR-0006](../../decisions/ADR-0006-evaluator-panel-sessions-and-github-pr-gate.md) G1-G3 →
> system 層 execution へ吸収）。本 spec の AC は機構を名指さない（承認の入力が GitHub PR の merge か
> ダッシュボードの承認かは HOW であって WHAT でない）。
>
> **meta-feature の層分け**: 本機能はハーネス自身の機構（外側の制御ループ）を作る。scoping guard の述語・
> 状態遷移（build-approved→needs-human-review→released）・観点集約は **system 層（execution）** が所有し、
> 本 spec は参照する（dependsOn は acceptance.yaml）。パネル採点そのものは別 spec（evaluator-panel・署名済み）で、
> 本 spec はその判定を**受けて**ゲートに載せる。
>
> **参照する固定制約**: [NORTH_STAR](../../NORTH_STAR.md)（自律は HOW まで・承認/审查は人間の判断点・
> false-pass を放置しない・状態は store で resume）／ evaluator-panel spec（sample 最終 verdict の供給元）。

## サブ機能一覧

> この一覧は設計層への分割境界ヒントであり、slice ではない。

| ID | サブ機能 | 優先度 |
| --- | --- | --- |
| LOOP-WATCH | 自律ドライブ（指定 issue を実装〜評価まで poll で継続的に進める・落ちても resume） | 高 |
| LOOP-GATE | 審査ゲート（approve を自動 released にせず人間判断で止め、その判断を証拠に残す） | 高 |

## LOOP-WATCH 自律ドライブ

**ユーザーストーリー**

- 誰が: このハーネスを使う人間
- 何を: 実装対象として明示指定した issue を、以後 HOW に触れず実装〜評価まで自律で進めてほしい
- なぜ: 北極星の「人間は WHAT だけ／HOW の自律」を、常駐する駆動として成立させるため。指定した issue が
  勝手に前進し、指定していないものは決して触られない、という信頼できる境界が要る

**事前条件**

- 対象 issue は実行可能（契約ドラフト済み・実装対象）で、かつ**実装対象として明示指定**されている
  （opt-in。未指定／他人所有はデフォルト非処理）。
- sample の最終判定の供給元（evaluator-panel）は署名済み・実装済み（本 spec はその判定を受ける）。

**受け入れ基準**

- **[AC-LOOP-001] 正常系: 指定 issue が人間の HOW 関与なく判定まで自律で進む**
  - Given 実装対象として明示指定された、実行可能状態の issue がある
  - When ドライブを回す
  - Then その issue は人間が HOW に触れることなく実装され評価され、判定（合格＝人間承認待ち、または要修正）に
    到達する。到達した状態は store に永続し、誰が見ても同じ現在地が分かる

- **[AC-LOOP-002] 境界: 指定されていない issue は決して触られない**
  - Given 実装対象として明示指定されていない issue（未指定／他人所有）が store に混在する
  - When ドライブを回す
  - Then それらの issue は処理対象にならず、status も成果物も一切変化しない（デフォルト非処理・opt-in）

- **[AC-LOOP-003] 耐障害性: 中断しても store の状態から resume する**
  - Given ドライブが issue を処理している途中で中断した（プロセスが落ちた等）
  - When 再度ドライブを回す
  - Then store の状態から在庫を再構成して継続し、既に完了した段の作業をやり直さない
    （揮発する実行状態でなく永続状態が現在地を決める）

- **[AC-LOOP-004] 耐障害性: 一巡は処理し尽くして終わり、再入で二重処理しない**
  - Given 複数の処理対象 issue がある
  - When ドライブの一巡を回す
  - Then その巡回は処理対象を処理し尽くして終了し、続けてもう一度回しても、同じ issue の同じ段を
    二重に処理しない（再入は冪等）

## LOOP-GATE 審査ゲート

**ユーザーストーリー**

- 誰が: このハーネスを使う人間
- 何を: 自律で合格まで来た成果を、自分が承認して初めてリリースにしたい。そして自分の承認/差戻しを
  証拠として残したい
- なぜ: リリースは人間の判断点（北極星: 承認/审查の自律はしない）。かつ、人間の判断とパネルの判定を
  同じ成果物に揃えれば、パネルの false-pass を運用から較正できる（改善の燃料）

**受け入れ基準**

- **[AC-LOOP-005] 正常系: 合格しても自動でリリースされず、人間の承認を待つ**
  - Given パネルが sample を approve（合格）にした issue がある
  - When ドライブがその判定を処理する
  - Then issue は自動で released にならず、人間の承認を待つ状態で停止する（合格＝released ではない）

- **[AC-LOOP-006] 正常系: 人間の承認でリリースされ、承認が証拠に残る**
  - Given 人間の承認待ちで停止している issue がある
  - When 人間が承認する
  - Then issue は released になり、その承認が当該評価の証拠（人間判定＝承認）として記録される

- **[AC-LOOP-007] 異常系: 人間の差戻しはリリースせず、差戻しを証拠に残す**
  - Given 人間の承認待ちで停止している issue がある
  - When 人間が差戻す
  - Then issue は released にならず、差戻しが当該評価の証拠（人間判定＝要修正）として記録される
    （＝パネルが誤って合格にした事例が、較正データとして運用から貯まる）

- **[AC-LOOP-008] 耐障害性: 承認判断の適用は冪等**
  - Given ある issue に人間の承認判断が下された
  - When 同じ承認判断が重複して適用される（再検知・再実行）
  - Then 二重にリリースされたり、証拠（人間判定）が重複記録されたりしない（同じ判断は一度だけ効く）

**非機能要件**

- 決定論: 駆動の制御（対象選定・段の前進・resume）は決定論で、同じ store 状態からは同じ次手が決まる
  （制御を非決定な判断に委ねない）。
- 可観測性: 各段の前進・承認/差戻しは、状態と証拠だけから resume・監査できる形で残る。
- セキュリティ/信頼境界: 承認は人間の判断点であり、自律側が自分でリリース承認を出さない。

**完了条件**

- 自動テスト: 正常（自律ドライブが判定まで到達／承認で released・証拠記録）／異常（差戻しで非 released・
  証拠記録）／境界（未指定 issue 不変）／耐障害性（resume・再入冪等・承認冪等）を各 1 以上。
- データ確認: 一巡後の永続状態（各 issue の status と、承認/差戻しの証拠記録）が期待どおりであること。

## レッドライン

> 実装が**絶対にしてはならない**こと。Generator への明示的禁止。

- 合格（パネル approve）を自動で released にしない（リリースは人間の判断点で止める）。
- 自律側が人間の承認/差戻しを自分で代行しない（承認の入力は必ず人間由来）。
- 実装対象として明示指定されていない issue を処理・変更しない（opt-in・デフォルト非処理）。
- 駆動の制御フロー（対象選定・前進・resume）を非決定な判断（LLM）に委ねない。
- 承認判断の重複適用で二重リリース・証拠の重複記録をしない。
- 承認の入力元の機構（GitHub PR 等）を本 spec.md に埋め込まない（HOW・設計層／ADR が持つ）。
