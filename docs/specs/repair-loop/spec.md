# 修復ループ（指摘を修正し、収束か上限まで繰り返す）受け入れ要件

> このファイルは Development Department への入力契約であり、人間が機能の **WHAT（受け入れ基準）** を
> 著す source of truth。frontmatter は持たない（meta・署名は ApprovedSpecRef が持つ）。
>
> **WHAT/HOW 境界**: 本 spec が定義するのは「パネルが要修正と判定したとき、その**観点横断の指摘を源に**
> 同じ成果物が修復され再評価される閉路が、**収束するか上限で止まるまで**回り、各試行が独立の証拠を残す、
> その**観測可能な性質**」。修復ブリーフの組み立て・再生成の機構・上限値は設計層／config が持つ（本 spec は
> 回数を数値で固定しない＝「有界」まで）。
>
> **meta-feature の層分け**: 本機能はハーネス自身の機構（修復閉路）を作る。修復ブリーフ（発生源観点付き）と
> パネル集約は既存 system 層（execution/evaluation）が所有し、本 spec は参照する（dependsOn は acceptance.yaml）。
> パネル採点・審査ゲートは別 spec（署名済み）で、本 spec はその間に**修復閉路**を挿す。
>
> **参照する固定制約**: [NORTH_STAR](../../NORTH_STAR.md)（同じ失敗を繰り返さない・証拠で評価・無言終了しない・
> 人間の判断点は残す）／ evaluator-panel spec（要修正判定と観点別指摘の供給元）／ execution-loop spec（ドライブと
> 審査ゲート）。

## サブ機能一覧

> この一覧は設計層への分割境界ヒントであり、slice ではない。

| ID | サブ機能 | 優先度 |
| --- | --- | --- |
| REPAIR-A | 修復閉路（指摘を源に再実装・再評価、収束でゲートへ・各試行の証拠） | 高 |
| REPAIR-B | 有界と昇格（上限で無限ループを断ち、未収束は人間審査へ） | 高 |

## REPAIR-A 修復閉路

**ユーザーストーリー**

- 誰が: このハーネスを使う人間
- 何を: パネルが要修正を出したら、その指摘を Generator が修正して再評価する、を自動で繰り返してほしい
- なぜ: 一発で通らない実装が普通であり、指摘→修正→再評価の閉路が自律開発の実効性を決める。人間は
  WHAT だけ、という北極星は、この修復が自動で回って初めて成立する

**事前条件**

- パネル（evaluator-panel）が sample を採点し、要修正のとき観点横断の指摘（発生源観点付き）を供給できる。
- ドライブ（execution-loop）が issue を実装〜評価まで進められる。本 spec はその評価が要修正だった後に閉路を挿す。

**受け入れ基準**

- **[AC-REPAIR-001] 正常系: 要修正の指摘を源に再実装され、再評価される**
  - Given ある試行がパネルで要修正（request_changes）と判定され、観点横断の指摘がある
  - When 修復ループが次の試行に進む
  - Then その指摘を**源に**（発生源観点を保ったまま）同じ成果物が再実装され、改めてパネルで評価される。
    再実装は前試行の指摘に由来し、本機能が指摘を新規捏造しない

- **[AC-REPAIR-002] 正常系: 上限以内に収束すれば審査ゲートへ進む**
  - Given 修復ループが回っている
  - When ある試行がパネルで合格（approve）に収束する
  - Then それ以上繰り返さず、issue は審査ゲート（人間承認待ち）へ進む（合格＝自動リリースではない）

- **[AC-REPAIR-003] 証拠: 各試行が独立した評価記録を残す**
  - Given 修復ループが複数試行を回した
  - When 記録を見る
  - Then 各試行がそれぞれ独立した評価記録（scorecard）を残し、初回と修復後を区別できる
    （初回合格率と最終合格率を別々に測れる）

## REPAIR-B 有界と昇格

**ユーザーストーリー**

- 誰が: このハーネスを使う人間
- 何を: 直らない実装で永久にループしてほしくない。上限で止めて自分に上げてほしい
- なぜ: 無限ループはコストと信頼を壊す。北極星「無言で終了しない・人間の判断点」を保つには、上限で
  止めて人間へ顕在化する必要がある

**受け入れ基準**

- **[AC-REPAIR-004] 境界/耐障害: 上限を尽くしても未収束なら停止し人間審査へ昇格**
  - Given 修復ループが、有界な上限回数まで繰り返しても合格に収束しない
  - When 上限に達する
  - Then それ以上繰り返さず（無限ループにならず）、issue は人間審査（needs-human-review）へ昇格し、
    静かに合格や放棄へ倒れない。上限までの各試行の証拠は残る

**非機能要件**

- 決定論: 修復の制御（次試行へ進む／収束で止める／上限で昇格）は決定論で、同じ store 状態からは同じ次手。
- 可観測性: 各試行の評価と、収束/昇格の結末は、状態と証拠だけから resume・監査できる。
- コスト: 繰り返しは有界（上限は設計層/config が持つ）。無限に評価を回さない。

**完了条件**

- 自動テスト: 正常（要修正→修復→再評価が指摘由来／上限以内の収束でゲートへ／各試行の独立証拠）・
  境界（上限で昇格・無限ループしない）を各 1 以上。
- データ確認: ループ後の永続状態（試行ごとの評価記録と、収束/昇格の最終 status）が期待どおり。

## レッドライン

> 実装が**絶対にしてはならない**こと。Generator への明示的禁止。

- 上限を無視して無限に繰り返さない（有界を破らない）。
- 未収束を静かに合格・放棄へ倒さない（上限では人間審査へ昇格する）。
- 修復の指摘を本機能が新規捏造しない（パネルの観点別指摘のみを源とする）。
- 収束（合格）を自動でリリースにしない（審査ゲートは execution-loop が持つ・人間の判断点）。
- 上限回数を本 spec.md に数値で焼き込まない（有界であることが WHAT・具体値は config/HOW）。
