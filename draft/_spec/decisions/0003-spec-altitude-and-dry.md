# 決定記録 0003: 仕様の高度（contract altitude）・薄い実装層・DRY の分担

- 状態: 確定
- 最終更新: 2026-06-15
- 影響モジュール: M21 Design Planner / M22 Design Reviewer / M06 Generator / M07 Evaluator /
  M03 Coordinator / M08 Repair Router / M10 Eval Curator / M12 Harness Analyst（foundation drift routing・D29）/
  全エージェント実装（横断原則）
- 正本差分: なし（REQUIREMENTS.md §3「契約ベース」「Coordinator はコード」「Evaluator は独立」を実装高度の
  原則として精密化するもの。上書きはしない）

## 1. 背景

Claude Code のドキュメントに「従来モデル向けの細かい指示は能力の高いモデルには過剰で出力品質を下げうる。
古い指示は見直し削除を検討せよ」という趣旨の記述がある。これを受け「今書いている事前設計は細かすぎないか」を
検討した。文言の射程は **モデルへの実行時指示（スキル/プロンプト）の粒度** であり、本ハーネスの spec
（エージェント間契約・不変条件・状態機械）とは層が違う——が、その境界は透過する。**spec は最終的にスキル/
エージェント定義として実装され、シグナル完成 → M03 ディスパッチで連携起動する**ため、spec の内容は実装時に
プロンプト内容になりうる。

そこで spec に含まれるものを仕分けたところ:

- **A. 決定的オーケストレーション**（状態機械・dispatch・ロック・版固定）= コード（M03）。プロンプトでない。
- **B. 契約・制約**（I/O スキーマ・モジュール間 interface・invariants・red lines）= スキルに載るが宣言形。
- **C. 手順・rubric**（HOW・内部設計・判定細則）= スキルに載ると肥大化し、能力の高いモデルの品質を下げる。

文言が直撃するのは C のみ。A は能力非依存（コード）、B は宣言ゆえ有能なモデルでも必要（準拠すべき契約は外から
要る）。むしろ独立評価・契約・SoT は**能力が上がるほど重要化**する（賢いモデルほど説得力をもって誤るため、
自己評価でなく証拠と独立検証が要る——北極星の非目標「評価なき自律を目指さない」）。

派生して「クラス内部設計を書かずに分解・レビュー・DRY が成立するか」を検討し、本 ADR で確定した。

## 2. 確定した決定（理由つき）

| # | 決定 | 理由 |
| --- | --- | --- |
| D26 | **contract altitude**: Tier1/Tier2（および各エージェント仕様）は **決定 + モジュール間契約 / seam + 制約**までの高度に留め、**クラス内部設計（クラス / メソッド / 内部データ構造・アルゴリズム）を書かない**。内部 HOW は実装（M06 Generator）に委ねる。記載テスト: 「**これが書かれていないと別の独立ユニット（他スライス / 他 PR / 他エージェント）が非整合になるか？**」Yes→契約として書く（B）/ No→局所決定に委ねる（C） | クラス内部は実装ユニットが局所決定でき、能力の高いモデルが文脈内でより良く決める。過剰な手順指示は出力品質を下げる。一方 seam / 契約は独立ユニットの相互運用に必要で能力非依存 |
| D27 | **DRY の分担**: アプリ全体の DRY は**設計時に保証しない**（実装レベルの大域創発特性）。三層で担保: ① Tier1 `sharedFoundations`（共通関心の所在・共有 seam の公開シェイプ）で**構造的に防止** ② `dependsOnSlices` の依存順で基盤スライスを先行させ後続が**既存コードを再利用** ③ 残余の私的重複は**実コードに対して検出・修正**。**契約レベル DRY**（責務重複・冗長境界）は M22、**実装レベル DRY**（再発明ロジック）は M07 | DRY はコード内部に跨る大域特性。独立実装する以上、各 Generator は他スライスの内部を見ず再発明し得る。これを上流クラス設計で潰すには Tier1 が実装をほぼ含む必要があり過剰仕様 + 陳腐化。構造防止 + 実装時検出が現実解。共有型は**公開シェイプ=契約(B・書く) / 内部表現=実装(C・委ねる)** |
| D28 | **薄い実装層 / 厳格さの置き場**: 不変条件・制約は可能な限り **コード / スキーマ validation / 独立評価（grader）** で強制し、エージェントのプロンプトは「ゴール + 契約形 + red line」の薄さに保つ。rubric・手順は焼き込まず、運用の証拠から起こし「その場でのスキル更新」に委ねる | 高性能モデル向けの指示は薄く保つ、という趣旨を正面から取り込む。ハーネスの中心思想（Coordinator はコード / grader / evidence）を徹底すれば、厳格さを保ったままプロンプトを薄くできる。危険は spec の不変条件を巨大な指示チェックリストとしてプロンプトに流し込む実装ミスのみ |
| D29 | **foundation drift（共有基盤の遡及的切り出し）= 第3の drift 源**。D27② で基盤が後から必要と判明した場合の規約。原則5点: ① **検出と抽出判断を分離**（検出=事実・コード/grader / 抽出可否=判断・M10/M21）② **再利用 > 抽出**（クリーンな既存単位が在れば consumer が再利用＝実装ループ内 M06/M08 で閉じ Tier1 を触らない。抽出は単位が無い時のみ設計ループへ）③ 抽出基準は**コード形状でなく知識同一性 / 同じ変更理由**（rule of three は代理指標）。**wrong abstraction を重複より恐れる**④ 遡及導入は**常に additive**（新 ARCH-ID `sharedFoundations` + 抽出/refactor スライスを新採番。既存 ID を renumber せず merged を巻き戻さない）⑤ foundation drift の**頻度を観測** → 高ければ「分解 / 基盤検出が下手」として M12 が M21 プロセスを改善 | DRY は知識（変更理由）の単一表現であってコード形状でない。形状ベースのしきい値自動抽出は偶然の重複を抽出し誤った抽象を量産する。再利用と抽出はコストが桁違いで、設計ループに上げるのは抽出のみ。additive 規約で ID 安定（D6）・SoT・append-only 履歴を守る。抽出基準自体が C（判断）ゆえ D28 に従い**原則のみ凍結・操作的 rubric は learn-on-the-fly**（しきい回数・結合度は焼き込まない） |

## 3. モジュール境界の畳み込み基準（D26 の系）

「能力の高いモデルならモジュールを減らせるのでは」への指針:

- **保持**（能力非依存に根拠がある境界）: 独立性（M07 / M22 の分離）・決定的コード（M03）・SoT（M18）。
  これらは「賢いモデルだから不要」にならない（独立評価は能力が上がるほど重要）。
- **再検討可**（タスク分解の都合に過ぎない境界）: 例 M05 resolve を M03 に畳む等は capability 向上で再考可。
- エージェント**内部**の分割（例 M21 が Tier1+Tier2+分解を1パスでやるか）は最初から薄く、モデルに委ねる。

## 4. なぜ「過剰計画」の逆か（可逆性）

| 種別 | 間違えた時の修正コスト | タイミング |
| --- | --- | --- |
| A/B（契約・境界・コード） | **高**（interface が波及） | **今確定** |
| C（rubric・手順・内部設計） | **低**（その場更新可） | **遅延・運用から学習** |

詳細に詰めるべきは A/B（高コスト側）であり、C は薄く遅延する。これは「変更が高くつく部分だけ先に固める」配分で
YAGNI と整合し、文言が警告する失敗（安い C を高コストな形で早期硬直）をむしろ回避する。

## 5. foundation drift の検出と routing（D29 の運用）

検出は時間軸で3点、応答は発見点で変わる。**設計ループ（遡及切り出し）に上がるのは「抽出」だけ**:

```text
M07（導入時・merge 前・shift-left）: 重複を検出 → 「再利用可能なクリーン単位が在るか?」
  ├─ 在る → repair instruction「既存 X を使え」→ M08 → M06 再利用（設計に上げない・安い）
  └─ 無い → M10 Curator へ（系統的重複として）
M10: 抽出すべきか判断（知識同一/同じ変更理由/rule of three/安定か）— wrong abstraction ガード
  └─ Yes → 設計 work order → M21 foundation drift（新 ARCH `sharedFoundations` + 抽出/refactor スライス・additive）
            → M22 が審査（過結合・誤った抽象でないか）
横断 DRY 監査（周期・コードベース横断）: 同時導入・歴史的重複を拾い同じ M10 経路へ
M12: foundation drift 頻度が高い → 「分解/基盤検出が下手」として M21 プロセス自体を改善
```

発見点ごとの ID 影響（additive を保つ）:

- **spawn 前**（M22 axis⑤）: 採番自由・retire 不要。既存の M21↔M22 ループで処理。
- **spawn 後 merge 前**（Generator が signal）: 依存側は被覆不変なら renumber 不要（dependsOn 辺追加 + gitSha 更新で
  M05 再 resolve）。基盤スライスのみ新採番。
- **merge 後**（M07 / 横断監査）: 全て additive。merged を巻き戻さず、移行は新 refactor スライス（新 sliceId）。

wrong-abstraction ガードは **M10/M21 の判断 + M22 の審査**に置く。M07 / 監査は**事実（重複の証拠）**を出すのみ
（検出器に判断を持たせない・D28）。

## 6. 残 open

- B（宣言すべき契約）と C（委ねる手順）の境界は各 FR で個別判断が要る。M01 抽出時に「契約 envelope に載せる/
  載せない」の規約として整理する。
- **横断 DRY 監査の所掌**（同時導入・歴史的重複を拾う周期パス）。M07 は per-PR ゆえ導入時しか捕まえられない。
  コードベース横断の監査を M12 Analyst 隣接に置くか M09 の専用 grader にするかは **M07/M09/M12 確定時**。
- D28 の「コードで強制 vs プロンプトで宣言」の振り分けは、M09 grader / M16 schema validation の確定と連動。
